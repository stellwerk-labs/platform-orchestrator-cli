# octl v2.1.0

This version changes deployment queue behaviour and secret-key output, and
adds platform Plugin Manager commands. Update automation before upgrading.

## Behaviour changes and upgrade actions

1. `deploy`, `rollback` and `score deploy` no longer print the age secret key
   that decrypts Runner logs. Add `--print-logs-key` to print it once after a
   warning. It cannot be combined with `--skip-logs`. Anyone who can read
   that output can decrypt the logs.
2. Those commands send `when_busy: queue`, also the Data Plane's new default.
   Busy Environments wait in the queue instead of failing immediately.
   `--no-queue` explicitly sends `when_busy: reject` to keep fail-fast
   behaviour. `--queue-ttl <duration>` bounds the queue wait; otherwise the
   server default is two hours. Ctrl-C leaves a queued request queued and
   prints the cancellation command. `--plan-only` and `--dry-run` never queue.
   Organisation-token requests still fail with `environment_busy` when busy.
3. `octl logs --key <key>` is removed. Use `--key-file <path>` or
   `--key-file -` for standard input. Input must contain exactly one age key;
   files written by `age-keygen` are accepted. This keeps the key out of
   command arguments and shell history.
4. `octl config set-token <token>` remains available but warns about exposure
   in shell history and process lists. Prefer `--token-file <path>` or
   `--token-file -`; input contains the token alone.

## Deployments and queue controls

- `--merge`, `--drop-workload`, `--drop-shared`, `score deploy` and
  confirmed diffs bind the expected base Deployment. Concurrent changes fail
  with `deployment_base_changed` instead of being overwritten.
- `--halt-on-failure` prevents a queued request from starting if the
  Deployment it waited for failed. The diagnostic reports
  `previous_deployment_failed` and the failed Deployment. Queue JSON/YAML
  carries `reason_deployment_id`; queue commands also show `halt_on_failure`.
- Plan-only and dry-run output warns when running or queued Deployments can
  change the result. A dry run can be answered beside a running Deployment;
  plan-only still refuses to run beside one.
- `environment_busy`, `deployment_queue_full`, `deployment_base_changed`
  and `outcome_unreconciled` diagnostics explain the next action.
- New commands list/read queue items, cancel queued requests and acknowledge
  an unreconciled outcome with a reason:
  `octl get deployment-queue-items`, `octl get deployment-queue-item`,
  `octl deployments cancel-queued`, and
  `octl deployments acknowledge-outcome --reason`.

## Plugin Manager

`octl plugin-manager` (alias `pm`) registers packages, installs/resumes,
activates, enables/disables, upgrades, uninstalls/reinstalls, purges, manages
organisation enablement and imports entitlements. Mutations require a reason,
carry expected revisions and use derived idempotency keys. Read commands expose
packages, installations and audit events.

Plugin identities are IAM platform principals belonging to no organisation.
`create-identities <installation>` creates the workload-bound principal and
a separate static-token admission checker, then records them on the installation.
The checker token appears once in JSON/YAML output; protect it as a secret.
If recording fails after creation, retry with `--admission-checker <id>`.
Creating the workload binding requires a user token with
`plugin_workload_binding_write`.

Install in this order: `install`, `create-identities`, start the runtime,
then `install --resume --enable-org ...`. Existing identities can be recorded
with `install --service-user ... --admission-checker ...`.

`organization-mode <installation> all|selected` controls organisation coverage.
Mode `all` enables active and future organisations; `disable-org` opts an
organisation out. `remove-org` is refused in mode `all`. Pending organisations
and licence organisation limits are shown with the next operator action.
Results include timezone, approval policy, capability registration and covering
licence grants. A licence grace warning prints once per command to stderr.

The plugin contract is `v1alpha` and supports only first-party Stellwerk plugins.
An enabled installation can serve multiple organisations sharing the plugin's
database; the Orchestrator checks organisation scope on each effect. Install
only reviewed packages. Plugin packages are distributed separately from the
Orchestrator and this CLI.

## Trust, upgrade and recovery

`PO_CA_FILE` adds a private CA bundle to the system trust roots.

Back up configuration, credentials and deployment state before upgrading.
Review scripts for the queue and secret-input changes above. Do not assume an
older server ignores new fields correctly; that compatibility is not qualified.
For coordinated server upgrades, retain additive database migrations. After
new-schema writes, recover with a reviewed compatible application revision or
forward repair rather than old writers or database Down migrations.

## Compatibility and distribution

The target compatible server set is CP 3.1.0, DP 4.0.0 and IAM 2.5.0.
Verify the selected artifacts and coordinated set before upgrading.
Distribution channels are signed binaries, the `ghcr.io/stellwerk-labs/octl`
container image, Homebrew and Scoop. Select version 2.1.0 when installing.
